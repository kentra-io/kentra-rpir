# A mod hook observes every Agent-tool subagent dispatched by the main session: agent.spawn exposes the full prompt, subagentType and an id that later matches the subagent's tool calls and its completion (turn.complete or $.agent.list status), so the mod can map each subagent to milestone M<n> and role impl|verify and time it from start to finish

Verdict: verified (confidence: high)

Evidence: docs: /private/tmp/claude-501/bundled-skills/2.1.301/3455b09f838254e0de91fd73a4243b8b/plugin-authoring/types/claude-code.d.ts@2.1.301

The mod API typings shipped with Claude Code 2.1.301 state the whole chain directly. `agent.spawn` "Fires when the Agent tool, or a workflow script's agent() ... is about to start an agent", and `$.agent.spawn` is "the same call the engine makes when the Agent tool starts one", so a hook on it sees the main session's Agent-tool dispatches. `AgentSpawnInput` carries `prompt` ("the Agent tool's prompt parameter"), `subagentType` (the resolved type, e.g. `kentra-rpir:implementer`), `description`, `tool_use_id`, `background` and `parentAgentId` (absent from main). The id is NOT known at spawn time: `AgentSpawnResult.agentId` is "set by core" and `next(e)` "resolve[s] once the subagent started", so the hook does `const r = await next(e)` and keeps `r.agentId` (a hook that answers without `next` started none). The same string is "the same string its loop's `tool.call` events carry as `agentId`" (ToolCallInput includes AgentLoop `agentId`, absent on main), and `turn.complete` carries `agentId` ("a subagent's id, as `$.agent.spawn` resolves it", "Every hook hears an agent's end"), with `durationMs` per turn and `reason` answer|aborted|refusal|error; `$.agent.list()` returns `{id, type, description, status, parentId}` with status pending|running|waiting|idle|completed|failed|killed. Timing source: `$.clock.now()` "Resolves milliseconds since the epoch"; start can be stamped when `next(e)` resolves and end at `turn.complete`, or use `durationMs`. Parallel subagents are separable because every record is keyed by `agentId` (also `tool_use_id` on the spawn input). Mapping to milestone and role is done by parsing `e.prompt`: the implement skill's prompts begin "You are implementing|verifying milestone M{{number}} `{{slug}}`", and `subagentType` independently gives role (kentra-rpir:implementer vs verifier). That regex relies on the plugin's own prompt text, not an API guarantee; the hook may also rewrite prompt, so read it before calling `next`.

Gaps:
- Background subagents: the typings say `background` is a flag on the spawn and that a spawn "runs in the background" for plugin-raised calls, and that a subagent's answer is its `turn.complete`, but no sentence explicitly says turn.complete fires for a model-dispatched `run_in_background` Agent; a throwaway-mod spike would confirm. The implement skill dispatches from the main session and normally waits, so impact is low.
- Ordering race: not stated whether a subagent's first `tool.call` can reach the mod before the `agent.spawn` hook's `await next(e)` returns and stores the id; handle unknown agentIds by buffering and attributing via `$.agent.list()` (which gives type and description) once known.
- A subagent resumed via SendMessage/resume yields further turn.complete events for one id (`resume.agentId`, "each run of its loop one turn"), so "completion" should be per-turn or defined by `$.agent.list` status; not tested.
- Official docs pages (code.claude.com/docs mods) and the changelog were not fetched; the verdict rests on the version-pinned typings only, and no run was executed (per instructions).
