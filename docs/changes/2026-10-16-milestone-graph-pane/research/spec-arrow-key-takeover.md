# A mod can take over Up and Down in its pane: a ui.scroll hook (graph taller than the pane) and a ui.focus hook (graph fits) can stop the engine's move, and $.ui.focus({ requestId, key }) plus $.ui.scroll can select the next box's header Button and keep it in view, telling arrow keys apart from the wheel and from the mod's own scrolls

Verdict: unverified (confidence: medium)

Evidence: docs: /private/tmp/claude-501/bundled-skills/2.1.301/3455b09f838254e0de91fd73a4243b8b/plugin-authoring/types/claude-code.d.ts@2.1.301 (the `ui.scroll`, `ui.focus`, `UiScrollInput`, `UiFocusInput`, `UiScrollArgs`, `UiFocusArgs` typings)

The typings for 2.1.301 support most of the premise. The `ui.scroll` hook "Fires before a site's window moves: the person's wheel or scroll keys on a `Pane` body ... `$.ui.scroll`", and "no `next` (`{}` or `{ deny }`) leaves it undrawn", so a hook that does not call `next` stops the engine's move. The `ui.focus` hook "Fires before a site's focus ring moves: the person's Tab, arrows or click in a `Pane`", and "no `next` ... keeps it where it was", so it can stop an arrow's focus move when the graph fits. `$.ui.focus({ requestId, key })` moves the ring "onto an element it drew there ... while it holds the keys" (a site that does not hold the keys is `{ deny }`; a key not yet drawn is awaited, bounded). `$.ui.scroll({ to: { key }, in, block })` reveals an element by key, `nearest` by default, as the DOM's `scrollIntoView` does. Both calls come back as events with `origin.kind: 'plugin'`, so the mod's own scrolls and focus moves can be told from the person's.

Telling an arrow from the wheel is the weak point. The `by` field cannot do it: "a wheel tick `-1` or `1` at rest, more as ticks crowd or summed in flight; an arrow a row while the engine has rows to scroll, a page key `bodyRows`, Home and End `contentRows`". An arrow and a single wheel tick are both +-1. The typings do offer another field: `pointer` ("The body cell the person's wheel or trackpad was over ... absent for the scroll keys and for `$.ui.scroll`"). So `pointer` present means wheel, and `pointer` absent with `origin.kind === 'person'` and `|by| === 1` means an arrow (or a plugin's own move, which has `origin.kind === 'plugin'`). PageUp/PageDown are `|by| === bodyRows` and Home/End are `|by| === contentRows`, so they can be passed through with `next(e)`. A wheel-tick burst can sum to a larger `by`, but it still carries `pointer`. This fits the lead's fallback (treat `|by| == 1` as selection moves) and improves on it, because the wheel need not move the selection.

The previous spike (`spikes/spec-diff-review-the-mod-ui-can-draw-a-gutter-of-lane-charac/result.md`, runs e3 to e5 on 2.1.301 in tmux) is a field report. With a graph taller than the pane, Down scrolled the body with no `ui.focus` event and Enter after it pressed nothing, Tab walked the header Buttons, and with a graph that fit (e2b) Down moved focus and Enter pressed. This matches the typings: the arrows scroll while the engine has rows to scroll, and walk focus otherwise.

On premise P11: the reference says `claude plugin test <folder>` mounts a component and acts "by key (`press`, `input`, `find` ...)", and that "The kit exercises the plugin's hooks ... not any surface's paint". It documents `press` by key, `input` and `select`, but no raw key presses (Up, Down, Tab, PageDown) and no scroll offset. So the test kit can assert that a press by key calls the mod's handler, and probably can raise `ui.scroll` and `ui.focus` events through hooks. It does not appear able to drive real arrow keys or assert the engine's scroll position or focus ring. Real arrow, wheel and PageDown behaviour needs a live tmux run.

Not settled from docs and source alone: no run has called `$.ui.focus` and `$.ui.scroll` from inside a `ui.scroll` hook (hook re-entrancy, the "another move came first" deny), and none has tested `pointer` or `by` live for a real wheel tick against a real arrow press.

Gaps:
- No live test that a `ui.scroll` hook returning `{}` (no `next`) stops an arrow's scroll in a pane taller than its content area, and that the mod then selects the next header Button.
- Calling `$.ui.focus` and `$.ui.scroll({ to: { key } })` from inside a `ui.scroll` hook is untested. It may re-enter the hook chain or be denied with "another move came first".
- The `pointer` distinction between wheel and arrow rests on the typings alone; no live wheel tick has been observed in tmux (tmux mouse input is awkward to send).
- Whether a ui.focus hook sees arrow origin as `person` with no way to tell an arrow from Tab (both are origin `person`; the typings give no key field) is unsettled. The mod may need to track Up/Down intent through the ui.scroll path only.
- P11: whether `claude plugin test` can send raw key presses or assert scroll/selection is not stated in the docs read; the source was not available, only the bundled typings and reference.
- No changelog or public web source was checked; only the bundled 2.1.301 typings and reference, and the prior spike's results.

## Spike verdict

VERDICT: verified — In live 2.1.301 terminal sessions a pane mod's ui.scroll hook (overflowing graph) and ui.focus hook (fitting graph) both stop the engine's arrow move, and $.ui.focus plus $.ui.scroll({to:{key}}) select the next header Button and keep it in view, with arrows told apart from the wheel (pointer), from page keys (|by|) and from the mod's own moves (origin plugin); caveats: in a fitting graph arrows are indistinguishable from Tab and wrap, and claude plugin test cannot press keys or assert selection.

The judge re-ran all nine experiments, and they reproduced line for line (record: `spikes/spec-arrow-key-takeover/result.md`). In a pane whose graph overflows (14 boxes, docked 42 body rows and inline 13 body rows), every Up/Down reached the mod's `ui.scroll` hook as origin person with `|by|=1` and no `pointer`, even at the top and bottom edges. Returning `{}` stopped the engine's scroll. `$.ui.focus({ requestId, key })` and `$.ui.scroll({ to: { key }, in })`, awaited or fired from inside the hook, both returned ok. The selection walked box by box A to J and back with the selected header on screen in 20 of 20 captures, and Enter pressed it. The wheel carries `pointer`, PageUp/PageDown arrive as `by=±bodyRows` and Home/End as `by=±contentRows`, so all three pass through untouched. The mod's own `$.ui.scroll` never re-entered its `ui.scroll` hook. Its own `$.ui.focus` re-entered its `ui.focus` hook as origin plugin. When the graph fits (2 or 3 boxes), the arrows raise only `ui.focus` with origin person: the same event as Tab, so the two cannot be told apart. The engine walks the header Buttons itself and wraps at the ends. A `ui.focus` hook returning `{}` froze the ring for both arrows and Tab, so a mod can clamp at the ends, but it cannot tell an arrow from Tab when it does. In the inline fitting run, a Tab followed by Enter closed the pane, which suggests that Tab, unlike the arrows, can land on the close mark (inferred from the captures). `claude plugin test` can raise synthetic `ui.scroll` and `ui.focus` events and check how the hooks route them. It has no implementation for `$.ui.focus` or `$.ui.status` and no raw-key act on a Pane, so it cannot test selection or scroll (P11 refuted at that level). The desktop surface was not run live.
