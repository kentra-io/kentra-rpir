# The mod UI can draw a gutter of lane characters to the left of a column of milestone boxes and keep each lane row lined up with the boxes. Each box's height changes over time (the current-tool-call line appears and disappears, and the attempts and wall-clock lines appear later). Arrow-key focus and Enter still work per box (req 16).

Verdict: unverified (confidence: medium)

Evidence: docs: plugin-authoring/types/claude-code.d.ts@2.1.301

The mod UI has the pieces to do this, but no source states the lined-up gutter directly, so I cannot confirm it. A Box takes `flexDirection: 'row'`, `alignItems`, `width`, `height`, `minHeight` and `overflow: 'hidden'`. Text takes `wrap: 'truncate-end'`, so text is cut rather than wrapped (req 17), and the terminal is monospaced with one cell per character. Because lines are cut rather than wrapped, the mod knows each box's height when it draws: it builds the box's lines itself, so it can emit a gutter string with the same number of lines. A per-milestone row Box would hold a gutter Text next to the box column. A shared flex row would also let the layout keep the two aligned, since both sit in one row Box. The pane's width is `e.props.bodyColumns`, and `ui.render` redraws on `$.ui.invalidate` and on state changes. Nothing in the types gives a fixed row grid or a measured box height, but neither is needed on this design. The "one preformatted text block" fallback that the topic lead worries about is not forced.

The real risk is req 16 and the Button. The `ButtonProps` doc says Button children are strings and `Text` only: "any other element is refused". A bordered multi-line Box therefore cannot sit inside a Button. The terminal draws a Button as `[ label ]`, and the types do not say whether a Button holding multi-line text draws on several rows. A safe design is a bordered Box with one Button for the header line (`M<n> <slug>`) and Text lines below it. That design has the Button as the only focus target per box, and the Enter press would belong to the header only. Reference.md line 158 says that in a pane opened with `focus`, "Tab and the arrows walk its buttons", and Enter raises `ui.press`. Per-Button focus with arrows and Enter therefore exists, and `key` can address each Button (the doc says to set `key` explicitly when a Button holds changing children). The spec's P4 covers only docking, throttling and `$.ui.view`; it does not cover this layout or the Button restriction. Arrow focus in a pane that was opened unasked, and without `focus`, is also not documented.

Neither the real terminal rendering nor the Button's multi-row behaviour was checked, and no code was run. A spike that draws two bordered rows of different heights with a gutter beside them, plus a press, would settle it.

Gaps:
- No primary source says a Button can draw multi-line children or that a row Box lines gutter rows up with boxes of varying height. This is inferred from the Box and Text props.
- Whether arrow keys move between Buttons across separate row Boxes (not a single Box) in a Pane is unconfirmed beyond "Tab and the arrows walk its buttons".
- Terminal rendering of `alignItems: 'stretch'` against a multi-line Text in a bordered column was not observed.
- Whether the pane takes the keys when opened unasked (no `focus`), as req 16 assumes, is not documented.

## Spike verdict

VERDICT: refuted — the lane gutter does stay aligned with boxes of changing height (if every header Button label is cut to one row), but when the graph is taller than the pane the arrow keys scroll instead of moving between boxes; only Tab walks the per-box Buttons for Enter, so req 16 fails as written.

The judge re-ran all six experiments on Claude Code 2.1.301, and each matched the designer's output. In the plugin test kit (terminal and desktop), a row Box per milestone holding a gutter column and a bordered box passed validation. The gutter line count equalled the box height at every tick as heights changed, and each box's header Button pressed by its own key. A Button holding a bordered Box was refused ("holds strings and Text, not <Box>"). In live tmux paints, the gutter and boxes stayed aligned on every row: 0 misaligned rows across the 14-milestone docked and inline runs, through height changes and scrolling. The one exception was the run with an uncut header Button label (e2b). The terminal wrapped that label onto 4 or 5 rows and misaligned 29 rows in box B, so the mod must cut header labels to the pane width itself. Arrow focus held only while the whole graph fit the pane (e2b: Down, Down, Enter pressed A). With a tall graph (e3, e4, e5), Down scrolled the body, raised no `ui.focus` event, and the Enter after it pressed nothing. Tab walked A, B, C and Enter pressed C. An inline pane got only 13 rows, so this is the common case. Req 16 should name Tab, or Tab and the arrows, as the keys that move between boxes, and P4 should note the one-row header label and the Button-holds-only-Text limits.
