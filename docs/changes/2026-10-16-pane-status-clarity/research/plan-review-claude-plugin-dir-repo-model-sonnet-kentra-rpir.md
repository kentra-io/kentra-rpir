# `claude --plugin-dir <repo> --model sonnet "/kentra-rpir:implement <folder>"` starts an interactive session whose first prompt runs the plugin's implement skill.

Verdict: unverified (confidence: medium)

Evidence: docs: https://code.claude.com/docs/en/cli-reference

Each part of the command is documented on its own, but no page says the combined form works. The CLI reference lists `claude "query"` as "Start interactive session with initial prompt". `--plugin-dir` is documented as "Load a plugin from a directory or `.zip` archive ... for this session only" (example `claude --plugin-dir ./my-plugin`). `--model` is documented as "Sets the model for the current session with a model alias such as `sonnet`, `opus`, `haiku`, or `fable`, or a model's full name", so the `--model sonnet` addition the plan makes is valid. The plugins/create page says a plugin's skills are namespaced by plugin name ("you run this one as `/my-first-plugin:hello`"), and that after `claude --plugin-dir ./my-first-plugin` you type `/my-first-plugin:hello` in the session. A kentra-rpir plugin therefore exposes `/kentra-rpir:implement`. The plugin root passed to `--plugin-dir` must be the directory holding `.claude-plugin/plugin.json`, not a marketplace root, which loads silently with no plugins. The harness checkout holds the plugin in the `kentra-rpir` submodule, so the demo script must pass that directory as `<repo>`. The remaining gap is that the docs show the slash command typed inside the session, not passed as the positional initial prompt. In practice a leading slash in the initial prompt is expected to be dispatched as a command, but I found no doc statement or source that confirms it, so confidence stays at medium. No code was run.

Gaps:
- No primary source states that a positional initial prompt beginning with `/plugin:skill <arg>` is dispatched as a slash command or skill. A one-time manual run of the command settles it.
- Whether the implement skill is user-invocable (not marked `disable-model-invocation` or otherwise hidden from slash invocation) was not checked against its SKILL.md.
- The version of Claude Code the demo will run on was not pinned or checked. The docs fetched are the current ones.
- Spec premise P4 (a `--plugin-dir` plugin overrides an installed plugin of the same name) was not checked. The docs link to "Name conflicts" in plugins/loading, which I did not read.

## Spike verdict

VERDICT: verified — run under a pty, the command starts an interactive Sonnet 5.5 session whose positional `/kentra-rpir:implement <folder>` runs the implement skill from the --plugin-dir checkout, once any first-run trust/MCP/imports dialogs are answered.

On Claude Code 2.1.301 the judge re-ran all six experiments. The headless proxy (E2) showed `--model sonnet` resolving to claude-sonnet-5-5 and `kentra-rpir` loading from this checkout (`kentra-rpir@inline`, version 0.5.0), with `kentra-rpir:implement` registered. Its reply cited `roles.impl-orchestrator.model`, which comes from skills/implement/SKILL.md, so the skill body was loaded. In all four interactive pty runs (E3 in the repo, E4 to E6 in throwaway dirs) the positional slash command ran as the implement skill with no keystrokes: each session checked the folder and read config and sessions.map, and asked which change to implement. This differs from the designer's E3 to E5, which timed out on startup dialogs (folder trust, a new .mcp.json server, external CLAUDE.md imports). In my runs those dialogs did not reappear, because the earlier answers persisted. E4's own `RESULT: timeout` marker is a false negative: its screen shows the skill running. The script also exceeds the 120 s limit. One caveat for run-demo.sh and the README's "Trying it." paragraph: a fresh project dir shows at least the folder-trust dialog, whose default is "No, exit", before the first prompt runs, so the user must accept it. The SKILL.md frontmatter sets neither `user-invocable` nor `disable-model-invocation`, so the skill is slash-invocable by default. P4 (overriding an installed plugin) was not tested here.
